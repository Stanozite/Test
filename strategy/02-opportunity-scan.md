# 🎯 3 Finalists ที่เสนอเข้า Phase 2

> **นี่คือข้อเสนอ ไม่ใช่การตัดสินใจ** — การตัดสินใจเกิดที่ Gate 2 ด้วยหลักฐานจาก probe

## F1 — Outcome Verification Layer `(D2 + D3 + B2)` · 69 คะแนน

**ประโยคเดียว**: *เป็นคนกลางที่พิสูจน์ว่า "งานที่ agent ทำ นับเป็นผลสำเร็จจริงไหม" ให้กับบริษัทที่ขายแบบจ่ายต่อผลลัพธ์*

**ทำไมมันน่าจะจริง**:
- outcome pricing **เกิดแล้ว ไม่ใช่ทฤษฎี** — Zendesk $1.50/automated resolution, Intercom Fin $0.99/resolved conversation, ตลาดทั่วไป $0.50–2.00
- Zendesk คิดเงิน**เฉพาะเมื่อ AI ปิดเคสเองโดยไม่มีคนแตะ** ล้มเหลว = ไม่คิดเงิน → **ผู้ขายแบกความเสี่ยง 100%**
- เมื่อผู้ขายแบกความเสี่ยง เขาจะยอมจ่ายแพงมากเพื่อ (ก) รู้ว่าจะสำเร็จไหมก่อนรับงาน (ข) พิสูจน์ต่อลูกค้าว่าสำเร็จจริง
- Deloitte ออกเอกสารเรื่อง**การบัญชี**สำหรับ outcome-based pricing (มิ.ย. 2026) = ปัญหาไปถึงฝ่ายการเงินแล้ว ไม่ใช่แค่ฝ่ายเทค

**Moat = ความเป็นกลาง** ⭐ นี่คือเหตุผลที่ vendor ทำเองไม่ได้: **ไม่มีใครยอมให้ผู้ขายเป็นคนตัดสินเองว่างานตัวเองสำเร็จ** — เหมือนผู้สอบบัญชี ต้องเป็นบุคคลที่สาม
บวก data ที่ทบต้น: นิยาม "outcome ที่นับได้" ต่อ vertical คือทรัพย์สินที่สะสมและลอกด้วยเงินไม่ได้

**จุดอ่อนที่ต้องพิสูจน์ให้ได้ก่อน**:
- ~~ตลาดยังเล็ก คนขาย outcome-based ยังนับหัวได้~~ → **พิสูจน์แล้วว่าผิด (2026-08-29)**: ~21.7% ของสัญญาซอฟต์แวร์องค์กร Q1 2026 เป็น outcome-based และ 60% เป็น hybrid
- ⚠️ **ความเสี่ยงตัวจริงคือกระจุกใน CX** — รายที่มีราคาประกาศชัดเจนเกือบทั้งหมดคือ customer support **ถ้า F1 ขายได้เฉพาะ CX มันคือ feature ของ CX platform ไม่ใช่บริษัท** นี่คือสมมติฐานที่ต้องฆ่าให้ได้ก่อน (ดู `probe1-target-list.md`)
- ⚠️ ผู้ซื้อคนแรกคือใครกันแน่: บริษัทที่ขาย agent (อยากพิสูจน์) หรือองค์กรที่ซื้อ agent (อยากตรวจสอบ)? **สองคำตอบนี้นำไปสู่คนละบริษัท**
- ⚠️ อาจถูก billing infra (Metronome/Orb/Stripe) กินจากล่างขึ้นบน → ต้องยืนที่ **"ตัดสินว่านับไหม"** ไม่ใช่ **"ออกใบแจ้งหนี้"**

## F2 — Self-building Eval `(B3 + B7)` · 65 คะแนน

**ประโยคเดียว**: *เปลี่ยน traffic จริงใน production ให้กลายเป็นชุดทดสอบเองอัตโนมัติ แล้วเตือนตอน agent เริ่มผิดแบบเนียน ๆ*

**ทำไมมันน่าจะจริง**: ทุกทีมรู้ว่าต้องมี eval แต่ไม่มีใครมีเวลาสร้าง golden set — **ปัญหาไม่ใช่ "ไม่มีเครื่องมือ" แต่คือ "ไม่มีข้อมูลจะใส่เครื่องมือ"** ตลาดวันนี้ขายเครื่องมือเปล่า

**Moat**: ทบต้นสูงสุด — ยิ่งลูกค้าใช้ eval set ยิ่งแม่นและย้ายออกยาก
**จุดอ่อน**: ชนกับ Braintrust/LangSmith โดยตรง ต้องแคบมากพอที่เขาไม่สนใจตามในปีแรก · และเป็น "vitamin" ในสายตาลูกค้าที่ยังไม่เคยเจ็บ

## F3 — Domain Ground-Truth Feed `(E1 + E2)` · 65 คะแนน

**ประโยคเดียว**: *ขายข้อมูลที่ถูกต้องและอัปเดตในโดเมนที่ผิดแล้วเสียเงินจริง (ภาษี/ศุลกากร/กฎระเบียบ/มาตรฐาน) ในรูปที่ agent กินได้ทันที*

**ทำไมอยู่ในลิสต์**: เป็น **hedge ที่ไม่ correlate กับ F1/F2** — ถ้าฟองสบู่ tooling แตก F1/F2 ตายพร้อมกัน แต่ F3 ไม่ตายเพราะลูกค้าคือคนที่มี P&L จริง ไม่ใช่คนที่มีเงิน VC
**Moat**: แข็งที่สุด (ข้อมูลสะสม + ความรับผิด) และ vendor ไม่แตะเพราะต้องรับผิดชอบความถูกต้อง
**จุดอ่อน**: เจ็บช้ากว่า · ต้องเลือกโดเมนให้ถูกตั้งแต่แรก · งานเก็บข้อมูลหนักและน่าเบื่อ (ซึ่งก็คือ moat นั่นแหละ)

## ⚠️ ข้อควรระวังเรื่อง portfolio (เขียนไว้กันตัวเองหลอกตัวเอง)

**F1 กับ F2 correlate กันสูง** — ลูกค้ากลุ่มเดียวกัน ตายพร้อมกันถ้าสมมติฐาน "verification จะยังแพง" ผิด
นี่เป็นความตั้งใจ (เพราะเชื่อสมมติฐานนั้นมาก) แต่ต้องรู้ตัว → **F3 คือประกัน ห้ามตัดทิ้งเพราะ "ไม่เท่"**

**สิ่งที่ตกรอบแต่ต้องเฝ้า**: `D4 SEO for agents` และ `C2 agent identity` — ทั้งคู่ตกเพราะ *ยังเช้าเกินไป* ไม่ใช่ *ไม่ดี* ถ้า signpost SP-8 ขยับ ให้ดึงกลับมาทันที
