# 03 — เกณฑ์ตัดสินใจ + Kill Criteria

> **เขียนไฟล์นี้เสร็จก่อนเปิด `02-opportunity-scan.md` เสมอ** — เกณฑ์ที่เขียนหลังเห็นตัวเลือกคือเกณฑ์ที่ถูกออกแบบมาให้ตัวเลือกที่เราชอบชนะ

---

## 1. Rubric ให้คะแนนโอกาส (0–5 ต่อข้อ)

| # | เกณฑ์ | น้ำหนัก | 0 = | 5 = |
|---|---|---|---|---|
| 1 | **ความเจ็บวันนี้** | ×3 | "น่าจะมีปัญหาปีหน้า" | มีคนบ่นออกสื่อ/มีคนแก้ด้วยมือทุกวัน |
| 2 | **มี budget อยู่แล้วไหม** | ×3 | ต้องสร้างงบใหม่ | มี budget line อยู่แล้ว แค่ย้ายผู้รับ |
| 3 | **ทนต่อ platform absorption** ⭐ | ×3 | vendor ship พรุ่งนี้ = จบ | ต้องอาศัยความเป็นกลาง/ใบอนุญาต/ข้อมูลสะสม |
| 4 | **คนเดียวสร้างได้ใน 8 สัปดาห์** | ×2 | ต้องมีทีม 5 คน | prototype ได้ใน 1 สัปดาห์ |
| 5 | **ขาย global ได้โดยไม่มีทีมขาย** | ×2 | ต้องบินไปเจอ | self-serve หรือปิดได้ทาง async |
| 6 | **ยิ่งทำนานยิ่งได้เปรียบ** | ×3 | ปีที่ 3 ก็เหมือนปีที่ 1 | data/integration/trust ทบต้น |
| 7 | **ต้นทุนถ้าคิดผิด** (กลับด้าน) | ×1 | เสีย 6 เดือนกว่าจะรู้ | รู้ผลใน 2 สัปดาห์ |

**คะแนนเต็ม 85** · เกณฑ์เข้า shortlist: **≥ 55** · เกณฑ์เข้า finalist: **≥ 62 และข้อ 3 ต้อง ≥ 3**

> ข้อ 3 เป็น **hard gate** ไม่ใช่แค่คะแนน — โอกาสที่ทำเงินดีแต่ตายเพราะ release note คือวิธีเสียเวลา 6 เดือนที่พบบ่อยที่สุดในสนามนี้

---

## 2. Anti-checklist — สัญญาณว่ากำลังหลอกตัวเอง

ถ้าเจอ 2 ข้อขึ้นไป ให้ลดคะแนนข้อ 1 ลงครึ่งหนึ่งทันที:

- [ ] อธิบายลูกค้าได้แค่ระดับ "ทีม AI ในองค์กร" ไม่ได้ระดับ "คนตำแหน่งนี้ ที่บริษัทแบบนี้ ที่กำลังทำสิ่งนี้อยู่"
- [ ] หลักฐานความเจ็บมาจากบทความ/รายงานเทรนด์ ไม่ได้มาจากคนจริงพูด
- [ ] เหตุผลที่ยังไม่มีใครทำคือ "ยังไม่มีใครคิดถึง" (แทบไม่เคยจริง)
- [ ] ตื่นเต้นกับ *เทคโนโลยี* มากกว่า *ปัญหา*
- [ ] ขนาดตลาดคำนวณแบบ top-down ("ถ้าได้แค่ 1% ของ...")
- [ ] เป็นของที่ **เราเอง**อยากใช้ แต่หาคนอื่นที่อยากใช้ไม่เจอ

## 3. Kill Criteria — เขียนล่วงหน้า ห้ามต่อรองภายหลัง

| ระดับ | ฆ่าเมื่อ | ทำอะไรต่อ |
|---|---|---|
| **ไอเดีย** | คะแนน < 55 หรือข้อ 3 < 3 | ตัดออกจาก shortlist ไม่ต้องเสียดาย |
| **Probe** | ยิงหา ICP 30 ราย ได้นัดคุย < 3 ราย ใน 2 สัปดาห์ | ฆ่า probe |
| **Probe** | คุย 10 ราย ไม่มีใครเคยพยายามแก้ปัญหานี้เอง | ฆ่า — ไม่เจ็บจริง |
| **Probe** | ขอ pre-pay/LOI 5 ราย ปฏิเสธหมด | ฆ่า — "สนใจ" ไม่ใช่ "จ่าย" |
| **Main bet** | 8 สัปดาห์หลัง v1 ยังไม่มีลูกค้าจ่ายเงินราย 3 | หยุด เขียน post-mortem ก่อนเริ่มอันใหม่ |
| **Main bet** | ลูกค้าจ่าย 10 ราย แต่ตอบไม่ได้ว่า "ยิ่งทำนานยิ่งได้เปรียบตรงไหน" | ยังเป็น *งาน* ไม่ใช่ *ธุรกิจ* — ตัดสินใจใหม่ |
| **ทั้งแผน** | signpost พลิก ≥2 ข้อในไตรมาสเดียว | กลับไป `01-world-model.md` |

**กฎเหล็ก**: kill criteria แก้ได้เฉพาะ **ก่อน**เริ่ม probe เท่านั้น แก้ระหว่างทางเมื่อไร = โกงตัวเอง

## 4. หลักฐานที่นับ vs ไม่นับ

| ✅ นับ | ❌ ไม่นับ |
|---|---|
| จ่ายเงินจริง (แม้ $1) | "น่าสนใจมาก ส่งข้อมูลมาหน่อย" |
| LOI / deposit / pilot ที่มีวันเริ่ม | ยอด waitlist |
| ยอมให้เวลาคุย 45 นาที **แล้วนัดต่อเอง** | ยอด like / star / upvote |
| แนะนำต่อให้เพื่อนโดยเราไม่ได้ขอ | คำชมจากคนที่ไม่ใช่ผู้ซื้อ |
| กลับมาใช้เองรอบที่ 3 โดยไม่ถูกเตือน | ใช้ครั้งแรกแล้วหาย |
| ถามเรื่องสัญญา/ความปลอดภัย/ราคาก่อนเราพูดถึง | บอกว่า "ไตรมาสหน้าน่าจะได้คุยกัน" |

**ประโยคที่ต้องท่องได้**: *ความสนใจฟรี ความมุ่งมั่นมีต้นทุน — เรานับเฉพาะอย่างหลัง*

## 5. Decision Register — สิ่งที่ยังไม่ตัดสิน และเส้นตาย

ตรงกับที่ตั้งใจไว้ว่า "ยังไม่เลือก" — ไม่เลือกตอนนี้ แต่กำหนดชัดว่าเลือกเมื่อไรและด้วยอะไร

| ต้องตัดสิน | ตัดสินเมื่อ | ตัดสินด้วยอะไร | สถานะ |
|---|---|---|---|
| **Product หรือ Service** | จบ Gate 2 | ผลของ money probe — อันไหนมีคนจ่ายก่อน | ⏸ รอ |
| **สนามไหน** (จาก 32 โอกาส) | Gate 1 เสนอ 3 → ยืนยันที่ Gate 2 | คะแนน rubric + หลักฐานความเจ็บจากคนจริง | 🔵 เสนอแล้ว รอพิสูจน์ |
| **ICP เจาะจง** | ระหว่าง Phase 2 | ใครตอบกลับและนัดคุยเร็วที่สุด (ไม่ใช่ใครที่เราอยากได้) | ⏸ รอ |
| **Pricing model** | Phase 3 | stage ของ ICP: S1 ขาย seat · S2 ขาย outcome | ⏸ รอ |
| **ช่องทาง GTM** | Phase 3 | ICP อยู่ที่ไหน — **ไม่ใช่เราถนัดที่ไหน** | ⏸ รอ |
| **จะระดมทุนไหม** | หลังลูกค้าจ่าย 10 ราย | ระดมเมื่อคอขวดคือ *เงิน* เท่านั้น ถ้าคอขวดคือ *ความรู้* การระดมทุนจะทำให้แย่ลง | ⏸ รอ |
| **จ้างคนแรกเมื่อไร** | หลัง MRR คงที่ 3 เดือน | จ้างเพื่อขยายสิ่งที่ work แล้ว ไม่ใช่เพื่อหาสิ่งที่ work | ⏸ รอ |

## 6. วิธีทดสอบว่า rubric นี้ใช้ได้จริง (ทำก่อนใช้)

เอา rubric ไปให้คะแนนธุรกิจที่ **รู้ผลแล้ว** อย่างละ 3 ตัว:
- 3 ตัวที่สำเร็จในสนาม dev tools/infra
- 3 ตัวที่ตายไปแล้ว (โดยเฉพาะ AI wrapper ปี 2023-2024 ที่ถูก vendor ดูด)

**ถ้า rubric ให้คะแนนสูงกับตัวที่ตาย → rubric พัง ต้องแก้ก่อนใช้จริง** โดยเฉพาะน้ำหนักข้อ 3
