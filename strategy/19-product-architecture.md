## 1. แกนเดียวที่ทุกอย่างหมุนรอบ

> ### รายงาน = อินพุต → ผ่านด่านกฎ → คำนวณ → ประกอบเป็นเอกสาร A4 → ส่งถึงลูกค้า → บันทึกไว้

**ชนิดรายงานเป็นข้อมูล ไม่ใช่โค้ด** — นี่คือข้อตัดสินสถาปัตยกรรมที่สำคัญที่สุดในไฟล์นี้

```
ReportType = {
  inputs      : อินพุตที่ต้องการ + อันไหนบังคับ
  calcs       : ชุดการคำนวณที่ต้องรัน
  scenarios   : สถานการณ์ที่เลือกใส่ได้
  template    : แม่แบบเอกสาร A4
  guards      : กฎข้อห้ามเฉพาะชนิดนี้ (เพิ่มจากกฎกลาง)
}
```

| รหัส | ชนิดรายงาน | สถานะ |
|---|---|---|
| **R-POLICY** | อ่านกรมธรรม์เก่าให้เข้าใจ | ✅ ตัวแรก |
| **R-FAMILY** | เซสชันครอบครัวปกป้องพ่อแม่ (`16`) | 🔜 ตัวที่สอง — **มีไว้เพื่อพิสูจน์ว่า abstraction ถูก** |
| **R-OVERVIEW** | ภาพรวมการเงินครัวเรือนหน้าเดียว | ภายหลัง |
| **R-RETIRE** | ช่องว่างเกษียณ | ภายหลัง |

**การทดสอบสถาปัตยกรรม**: ลองใส่ R-FAMILY ลงในโครงนี้**บนกระดาษ ก่อนเขียนโค้ด** — ถ้าต้องแก้แกน แปลว่า seam ผิด · แก้ตอนนี้ราคาเท่ากับลบย่อหน้า แก้ตอนมีโค้ดราคาเท่ากับเดือน

## 2. แผนที่โมดูล — 14 โมดูล 4 ชั้น

### ⚠️ อ่านก่อน: อย่า deploy เป็น microservice จริง

คนเดียวดูแล 14 services = **ตายด้วยงาน ops ไม่ใช่ตายด้วยตลาด**

> **รูปที่ถูกคือ modular monolith ที่มีขอบเขตระดับ microservice** — deploy ก้อนเดียว 14 โฟลเดอร์ มีกฎบังคับว่าใครเรียกใครได้ และคุยกันผ่าน interface ที่นิยามไว้

สิ่งที่การคิดแบบ microservice ให้จริงคือ **วินัยเรื่องขอบเขต** ซึ่งคือสิ่งที่ต้องการ · ส่วนต้นทุน ops ไม่ต้องจ่าย · **แยกออกเป็น service จริงเมื่อมีโมดูลที่ต้องสเกลหรือล้มแยกกัน ซึ่งตามจริงมีแค่ `extract`**

### ชั้น 1 — แกนร่วม (ทุกชนิดรายงานใช้)

| โมดูล | เป็นเจ้าของ | ทำไมต้องแยก |
|---|---|---|
| `identity` | ตัวแทน · หน่วย · บทบาท · **เลขใบอนุญาต** · การถอนสิทธิ์ | ถอนสิทธิ์ต้องมีผลทันทีและเป็นอิสระจากทุกอย่าง · เลขใบอนุญาตเป็นข้อมูลเชิงกำกับดูแล |
| `consent` | ความยินยอม · สิทธิขอดู/ขอลบ · นาฬิกาเก็บข้อมูล | ⭐ **เจ้าของข้อมูลคือลูกค้าของตัวแทน ไม่ใช่ผู้ใช้ของเรา** — ความยินยอมสามฝ่ายเป็นรูปที่ไม่ปกติ |
| `intake` | เอกสารดิบ · เซสชันอัปโหลด · คิวรออัปโหลด | ต้องเปลี่ยนวิธีรับข้อมูลได้โดยไม่กระทบใคร — วันนี้ถ่ายรูป พรุ่งนี้อาจดึงจากระบบกลาง |
| `audit` | **บันทึกเพิ่มได้อย่างเดียว ลบไม่ได้ แก้ไม่ได้** | เป็นหลักฐาน · วินัยการเก็บต่างจากข้อมูลทั่วไป (ดู `23` D8) |
| `billing` | จำนวนรายงาน · ใบแจ้งหนี้ · เพดานต้นทุน | คิดต่อรายงาน (`18 §6` ตัดสินแล้ว) |

### ชั้น 2 — ความรู้ (สินทรัพย์ที่ทบต้น)

| โมดูล | เป็นเจ้าของ | ทำไมต้องแยก |
|---|---|---|
| ⭐ `catalog` | คลังแบบประกัน · ถ้อยคำ · ข้อยกเว้น · **New Health Standard** · **เส้นแบ่ง 8 พ.ย. 2564** | **คูเมืองจริงของธุรกิจนี้** — ใคร ๆ ก็ prompt โมเดลได้ แต่คลังนี้ต้องสะสมทีละเล่ม · โตแยกจากทุกอย่าง |
| ⭐ `plainlang` | อภิธานศัพท์ · คำต้องห้าม · **เกณฑ์วัดความอ่านง่ายภาษาไทย** | ใช้ซ้ำทั้งธุรกิจ — เอกสาร · คอนเทนต์ Writer_Wealth · โปรโตคอลใน `16` |
| `scenario` | นิยามสถานการณ์ + วิธีคำนวณแต่ละอัน | ของที่ขโมยมาจาก SBC (`21 §2`) · โตทีละสถานการณ์ |

### ชั้น 3 — ประมวลผล

| โมดูล | เป็นเจ้าของ | ทำไมต้องแยก |
|---|---|---|
| `extract` | ฟิลด์ที่อ่านได้ + **ตำแหน่งที่อ่านมา (หน้า/กรอบ)** + ระดับความมั่นใจ | ส่วนที่เป็น AI · เปลี่ยนโมเดลบ่อยสุด · ต้องทดสอบกับชุดเฉลยแยกได้ · **โมดูลเดียวที่สมควรแยกเป็น service จริงในอนาคต** · ⛔ ต้องอยู่หลัง interface เพราะ C2 ยังไม่ตอบ |
| `calc` | **ไม่เก็บอะไรเลย — ฟังก์ชันบริสุทธิ์** | ⭐ **deterministic ทดสอบได้ 100% ห้ามมี AI ในนี้** — ตัวเลขผิดต่อหน้าลูกค้าคือความล้มเหลวที่แก้ไม่ได้ |
| ⭐ `guard` | กฎข้อห้าม + การตัดสินว่าบล็อกหรือเตือน | **ต้องเป็นโค้ด ไม่ใช่ prompt** — prompt หลบได้ โค้ดหลบไม่ได้ · และเพราะร่วมแบรนด์ นี่คือสิ่งที่ปกป้องเราเอง |

### ชั้น 4 — ส่งมอบ

| โมดูล | เป็นเจ้าของ | ทำไมต้องแยก |
|---|---|---|
| `render` | แม่แบบ · เอกสารที่ออกแล้ว · **เวอร์ชันของทุกอย่างที่ผลิตมัน** | เอกสารที่ลูกค้าถือต้องย้อนสร้างซ้ำได้เป๊ะ (`23` D1) · ความเนี้ยบตอนพิมพ์เป็นศาสตร์ของตัวเอง |
| `deliver` | LINE · พิมพ์ · **ลิงก์ที่เปิดได้โดยไม่ต้องสมัครอะไร** | ⭐ คน 70 — **ห้ามบังคับสมัครสมาชิกเพื่ออ่านเอกสารของตัวเอง** |
| `registry` | นิยามของชนิดรายงานทั้งหมด | ที่ที่ทำให้คำว่า "แพลตฟอร์ม" เป็นจริง · **ตรึงสัญญาก่อน R1 ขึ้น** (`23` D11) |

## 3. กฎการเรียกข้ามโมดูล — ทำเป็นกฎ lint ตั้งแต่โฟลเดอร์แรก

```
1. ชั้นล่างห้ามเรียกชั้นบน
2. calc ห้ามเรียกโมดูลอื่นเลย — รับค่าเข้า คืนค่าออก จบ
3. guard ถูกเรียกก่อน render เสมอ ไม่มีทางลัด ไม่มีธงข้าม
4. ทุกอย่างที่ออกสู่ลูกค้าต้องผ่าน audit ก่อน
5. extract ห้ามเขียนลงที่ไหนนอกจากตารางผลการอ่านของตัวเอง
6. ไม่มีโมดูลไหนอ่านตารางของโมดูลอื่นตรง ๆ — ผ่าน interface เท่านั้น
```

**ถ้ากฎข้อไหนถูกละเมิดแล้วยังรันได้ แปลว่ายังไม่ได้ทำกฎ lint** — เขียนกฎก่อนเขียนฟีเจอร์

## 4. เส้นทางของข้อมูลหนึ่งรายงาน

```
ตัวแทนกด "ทำรายงานใหม่"
   → registry  บอกว่า R-POLICY ต้องการอินพุตอะไร
   → consent   ⛔ ด่านแรก ไม่มีความยินยอม ไม่มีอะไรเกิดขึ้นต่อ
   → intake    รับรูป เก็บดิบ ตั้งนาฬิกาเก็บข้อมูล
   → extract   อ่าน → ฟิลด์ + ตำแหน่งที่อ่านมา + ความมั่นใจ
   → (ตัวแทนยืนยันทีละฟิลด์ — ฟิลด์ที่ไม่มั่นใจบังคับยืนยัน)
   → catalog   เทียบชื่อแบบประกัน → ถ้อยคำ ข้อยกเว้น มาตรฐานเก่า/ใหม่
   → calc      มูลค่าเวนคืน · ใช้เงินสำเร็จ · ขยายเวลา · เบี้ยสะสม
   → scenario  คำนวณสถานการณ์ที่เลือก
   → plainlang แปลทุกคำเป็นภาษาคน 70 + ตรวจระดับภาษา
   → guard     ⛔ ด่านสอง ไม่ผ่าน = ไม่ออกเอกสาร
   → render    ประกอบ A4 + ฝังเวอร์ชันทุกอย่าง
   → audit     บันทึกว่าแสดงอะไร เมื่อไร ใคร
   → deliver   ลิงก์ → ตัวแทนฟอร์เวิร์ดใน LINE / พิมพ์
```

**จุดที่หยุดได้มีสองจุดเท่านั้น**: `consent` และ `guard` · ที่อื่นหยุดไม่ได้เพราะไม่มีอะไรให้ตัดสิน

## 5. ข้อมูลกรมธรรม์ที่มีจริง — ฐานของ `extract` และ `calc`

### สิ่งที่อยู่ในเล่มที่ลูกค้าถืออยู่แล้ว

| ข้อมูล | อยู่ที่ไหน | อ่านได้ด้วยเครื่องไหม |
|---|---|---|
| ชื่อแบบประกัน · ประเภท · วันเริ่มสัญญา · ระยะเวลาคุ้มครอง · เบี้ย · งวดการจ่าย · ระยะเวลาจ่ายเบี้ย · จำนวนเงินเอาประกัน | **หน้าตารางกรมธรรม์** | 🟢 น่าจะได้ — `[รอข้อมูลจริง]` |
| ⭐ **ตารางมูลค่ากรมธรรม์** (เวนคืน · ใช้เงินสำเร็จ · ขยายเวลา) **เป็นมูลค่าต่อทุนประกัน 1,000 บาท** | **ด้านหลังของทุกเล่ม** | 🟡 ตารางยาว ต้องทดสอบ — `[รอข้อมูลจริง]` |
| สัญญาเพิ่มเติม (ถ้ามี) — บันทึกไว้ในกรมธรรม์ | ในเล่ม | `[รอข้อมูลจริง]` |
| ข้อยกเว้น (ถ้อยคำสัญญา) | ในเล่ม | 🔴 ยาวและต่างกันตามแบบ → ต้องมี `catalog` |

### สูตรที่ `calc` ต้องทำได้ (ไม่มี AI เกี่ยวข้อง)

```
มูลค่าเวนคืน ณ ปีที่ n  =  (ค่าในตารางของปีที่ n)  ×  (ทุนประกัน ÷ 1,000)
มูลค่าใช้เงินสำเร็จ      =  วิธีเดียวกัน — ทุนลดลงตามตาราง แต่คุ้มครองถึงครบสัญญา
เบี้ยที่จ่ายไปแล้ว        =  เบี้ยต่องวด × จำนวนงวดที่จ่ายแล้ว
```

> ⭐ **ข้อเท็จจริงที่สำคัญที่สุดที่ `calc` + `catalog` ต้องผลิตออกมา**
>
> **เปลี่ยนเป็นกรมธรรม์ใช้เงินสำเร็จเมื่อไร สัญญาเพิ่มเติมทั้งหมดสิ้นผลบังคับทันที**
>
> สัญญาเพิ่มเติมคือความคุ้มครองสุขภาพ/โรคร้ายแรง ซึ่งเป็นตัวที่ **underwrite ใหม่ไม่ได้ถ้าสุขภาพเปลี่ยนไปแล้ว** · นี่คือข้อเท็จจริงที่มีประโยชน์ที่สุดต่อลูกค้า **และเป็นข้อเท็จจริงเดียวกับที่ปกป้องลูกค้าจากการถูกปล้นกรมธรรม์** — เครื่องมือนี้จึงปลอดภัยโดยโครงสร้าง ไม่ใช่โดยนโยบาย

### เส้นแบ่งที่ `catalog` ต้องรู้

**คำสั่งนายทะเบียนที่ 14/2564 · มีผล 8 พ.ย. 2564** — คปภ. กำหนดมาตรฐานประกันสุขภาพให้เป็นแบบเดียวกันทุกบริษัท ออกแบบมาให้ *"เปรียบเทียบได้ข้ามบริษัท"*

| | ก่อน 8 พ.ย. 2564 | ตั้งแต่ 8 พ.ย. 2564 |
|---|---|---|
| โครงสร้างความคุ้มครอง | ต่างกันทุกบริษัท | **มาตรฐานเดียวกัน** |
| การอ่านอัตโนมัติ | 🔴 ยาก ต้องสะสมรายแบบ | 🟢 เป็นไปได้จริง |
| การเปรียบเทียบ | ต้องระวัง | **หน่วยงานกำกับตัดสินแล้วว่าเทียบได้** |

→ และ **"กรมธรรม์สุขภาพของคุณเป็นแบบเก่าหรือแบบใหม่"** คือคำถามที่มีผลต่อชีวิตลูกค้าจริง แต่แทบไม่มีใครรู้คำตอบ · **เอกสารเราตอบได้ทันทีและฟรี**

## 6. ลำดับการสร้าง — ภาพรวมครบแล้ว เติมทีละโมดูล

```
R0  กระดาษ             ทำมือ 3 เล่ม · ศูนย์โค้ด · ศูนย์ infra
                        → ทดสอบกับคน 70 จำนวน 3 คน
R1  สคริปต์เครื่องตัวเอง  1 บริษัท 1 แบบประกัน · ถ่าย 1 รูป · ตรวจมือ 100% · ออก PDF · ส่ง LINE ด้วยมือ
                        โมดูลที่มีจริง: intake · extract · calc · render · guard · audit · consent
                        ⟵ ยังไม่ต้องมี Supabase · auth · Vercel · RLS
R2  ขยายการอ่าน         4 บริษัท · ตารางมูลค่า · 3 สถานการณ์ · PWA ถ่ายออฟไลน์
                        เพิ่ม: catalog · scenario · plainlang · deliver
R3  ตัวแทนใช้เอง         ⟵ สแต็กทั้งชุดเริ่มจำเป็นตรงนี้ (LINE Login · RLS · คิวงาน · Vercel)
                        เพิ่ม: identity · registry
R4  ขายเป็นหน่วย         billing · หน้าหัวหน้าหน่วย · สัญญาณเตือน
```

> ⭐ **`guard` · `audit` · ชุดเฉลยทดสอบความแม่น อยู่ใน R1 ไม่ใช่ R4**
> เพราะร่วมแบรนด์ทำให้สองอันแรกเป็นเกราะไม่ใช่ลูกเล่น · และ **การย้อนใส่บันทึกตรวจสอบทีหลัง คือวิธีที่ทำให้สุดท้ายไม่มีบันทึกตรวจสอบ**

**กฎกันตายของทั้งแผน**: **R1 ต้องถึงมือลูกค้าจริงได้ แม้จะอ่านได้แค่บริษัทเดียวแบบเดียว** · ถ้า R1 ยังไม่ถึงมือใคร แปลว่ากำลังออกแบบเพื่อความสบายใจ ไม่ใช่เพื่อใช้งาน — และ `10-pivot` บันทึกบทเรียนนี้ไว้แล้ว: *"สามรอบที่แล้วผลิตเอกสารเยอะ คุยกับลูกค้าศูนย์ราย อย่าทำซ้ำ"*

## 7. ความเสี่ยงที่สถาปัตยกรรมแก้ไม่ได้

| # | ความเสี่ยง | สถาปัตยกรรมช่วยไหม |
|---|---|---|
| 1 | ⛔ **C2 ยังไม่ตอบ** — ส่งข้อมูลกรมธรรม์ลูกค้าไปประมวลผลที่ผู้ให้บริการ AI ต่างประเทศได้ไหม | ไม่ — **ข้อนี้ล้มสแต็กได้ทั้งชุด** · บรรเทาได้แค่เอา `extract` ไว้หลัง interface |
| 2 | ความแม่นของการอ่านเล่มจริง | ไม่ — แก้ด้วยชุดเฉลยและการจำกัดสโคป |
| 3 | มีใครอยากได้ไหม | ไม่ — แก้ด้วย `18 §9` สัปดาห์ 3 |
| 4 | ⭐ **ตัวแทนที่อยากใช้มากที่สุดอาจเป็นคนที่เราไม่อยากให้ใช้** | บางส่วน — `audit` + `guard` + ถอนสิทธิ์ + หน้าสัญญาณเตือนของหัวหน้าหน่วย · **แต่การคัดคนยังต้องใช้วิจารณญาณ ไม่ใช่โค้ด** |

## 8. คำถามที่ต้องถามตัวเองตลอด

> ### "ระบบที่ออกแบบครบทุกโมดูลล่วงหน้า มักตายเพราะสร้างไม่เสร็จ ไม่ใช่เพราะออกแบบผิด"

เอกสารชุด `19`-`23` มีค่าก็ต่อเมื่อมันทำให้ **R1 ออกเร็วขึ้น** ไม่ใช่ช้าลง · ถ้าอ่านจบแล้วรู้สึกว่าต้องสร้าง 14 โมดูลก่อนส่งอะไรให้ใคร **แปลว่าอ่านผิด** — กลับไปอ่าน §6
