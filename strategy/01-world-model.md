# 01 — World Model: โลกเปลี่ยนยังไง และมูลค่าย้ายไปไหน

> เอกสารแม่ ทุกอย่างในโฟลเดอร์นี้ต่อยอดจากไฟล์นี้ · ทบทวนทุกไตรมาสเทียบ `06-signposts.md`

---

## 1. แก่นเดียวที่ต้องจำ

> **เมื่อการผลิตงานถูกลง คอขวดย้าย และมูลค่าย้ายตามคอขวดเสมอ**

ยุคก่อน: คอขวดคือ **การผลิต** (เขียนโค้ดไม่ทัน เขียนเนื้อหาไม่ทัน วิเคราะห์ไม่ทัน) → มูลค่าอยู่ที่คนผลิตเก่ง

ยุค agent: การผลิตเหลือเกือบฟรีและเกือบไม่จำกัด → **คอขวดย้ายไปที่ "การตรวจ" และ "การอนุญาต"**

นี่คือประโยคเดียวที่ทั้งแผนตั้งอยู่บน ถ้าประโยคนี้ผิด แผนทั้งหมดผิด (ดู tripwire ใน `06`)

**อุปมาที่ช่วยให้เห็นภาพ**: เหมือนโรงพิมพ์ที่พิมพ์ได้ฟรีไม่จำกัด ปัญหาจะไม่ใช่ "พิมพ์ยังไง" แต่เป็น "รู้ได้ไงว่าอันไหนถูก" และ "ใครยอมให้พิมพ์ในนามฉัน"

## 2. โซ่คอขวด — แผนที่ธุรกิจทั้งหมดอยู่ในบรรทัดเดียวนี้

```
ต่อระบบได้ → เห็นว่ามันทำอะไร → พิสูจน์ว่าถูก → จำกัดความเสียหาย → รับผิดได้ → ปล่อยให้ทำเอง → ให้มันจ่ายเงินเองได้
   (A)            (B1)              (B2)             (C1)            (C2)          (—)              (D)
```

**ทุกข้อต่อ = สินค้าได้อย่างน้อยหนึ่งตัว** และ agent จะไม่ถูกปล่อยให้ทำงานจริงจนกว่าจะผ่านครบทุกข้อต่อ
องค์กรส่วนใหญ่วันนี้ติดอยู่ที่ข้อต่อ 3–5 — **นั่นคือที่ที่เงินกอง**

### ของที่หายาก (scarce) หลังคอขวดย้าย

| ของที่หายาก | ทำไมยังหายาก | ใครจ่ายให้ | อยู่ได้นานแค่ไหน |
|---|---|---|---|
| **Verification** — รู้ว่าที่ทำมาถูกไหม | generate ถูกลง 100 เท่า แต่ "ตรวจ" ยังแพงเท่าเดิม ยิ่ง output เยอะยิ่งตรวจไม่ไหว | คนที่เอา agent ไปใช้กับงานที่พังแล้วเจ็บ | **ยาว** — ยิ่งโมเดลเก่งยิ่งตรวจยาก (ผิดแบบเนียนขึ้น) |
| **Permission / Identity** | ไม่มีใครกล้าให้ agent ถือ credential เต็มสิทธิ์ | ทุกองค์กรที่จะ deploy จริง | กลาง — มาตรฐานกำลังมา อาจถูกดูดโดย identity vendor |
| **Context เฉพาะ** | อยู่ในหัวคน ในไฟล์ ในระบบเก่า โมเดลไม่มีทางรู้ | คนที่จะ automate งานเฉพาะทาง | **ยาว** — สะสมได้ ลอกยาก |
| **Accountability** | agent รับผิดไม่ได้ ต้องมีนิติบุคคล/ประกัน/สัญญา | อุตสาหกรรมที่มี regulator | **ยาวมาก** — กฎหมายช้าที่สุด |
| **Real-world execution** | มือ ขา ใบอนุญาต ความสัมพันธ์ | ธุรกิจที่ไม่ได้อยู่บนจอ | ยาว (แต่เราไม่เล่นสนามนี้) |
| **Distribution** | ช่วงแรกคนกด ช่วงหลัง **agent เป็นคนเลือก** | คนที่มีของแต่ไม่มีคนรู้จัก | เปลี่ยนรูป — ดู S3 |
| **Compute / Energy** | ต้นทุนกายภาพ | ทุกคน | ยาว — **แต่แข่งไม่ได้ด้วยทุนระดับเรา ตัดทิ้ง** |

### กฎการอยู่รอดของ picks & shovels

> อย่าขายของที่ release note บรรทัดเดียวฆ่าได้

คำถามคัดกรองข้อแรกของทุกไอเดีย: **"ถ้า foundation model vendor ทำเองพรุ่งนี้ เราเหลืออะไร"**

คำตอบที่รับได้มีแค่ 5 แบบ:
1. **ข้อมูลที่สะสมเอง** — ยิ่งใช้ยิ่งดี ลอกด้วยเงินไม่ได้
2. **Integration น่าเบื่อจำนวนมาก** — ใครก็ทำได้ แต่ไม่มีใครอยากทำ 200 ตัว
3. **ความไว้ใจ / ใบอนุญาต / ความรับผิด** — ต้องมีนิติบุคคลรับผิด vendor ไม่อยากรับ
4. **Network สองฝั่ง** — คนซื้อกับคนขายต้องมาเจอกัน
5. **ความเป็นกลาง (neutrality)** — ⭐ **อันนี้สำคัญที่สุดและคนมองข้าม**: บางบทบาท vendor ทำเองไม่ได้เพราะ *conflict of interest* เช่น ใครจะเป็นคนตัดสินว่า agent ของ vendor ทำงานสำเร็จจริงไหม — vendor ตัดสินเองไม่ได้

## 3. ฉากทัศน์ S0 → S4

> **หมายเหตุสำคัญ**: ไม่ใส่ปี ใส่ **signpost ที่ตรวจสอบได้** แทน เพราะการทำนายปีคือวิธีหลอกตัวเองที่นิยมที่สุด
> โลกไม่ได้เดินพร้อมกันทุกอุตสาหกรรม — customer support อยู่ S2 แล้ว ขณะที่ legal/healthcare ยังอยู่ S0-S1

### S0 — Copilot (agent นั่งข้างคน)
- **โลก**: คนกดทุกปุ่ม agent เสนอ คนตัดสิน · ผลิตภาพขึ้น 10-30% ในงานที่วัดยาก
- **เงิน**: seat/เดือน — **จริงและใหญ่แล้ววันนี้** แต่บาง churn สูง เพราะพิสูจน์ ROI ยาก
- **ตัวเร่ง**: ราคา token ลง, UX ง่าย, การแข่งขันบีบให้ทุกคนต้องมี
- **ต้องมีก่อน**: แค่ browser
- **สถานะ**: ✅ ผ่านไปแล้ว — **ไม่ใช่ที่ของเรา ตลาดอิ่มตัวและ vendor เป็นเจ้าของ**

### S1 — Delegated task (agent ทำงานเป็นชิ้น จบเอง คนรีวิวท้ายทาง)
- **โลก**: มอบงานที่มีขอบเขตชัดให้ agent ทำจบ คนกลายเป็นคนรีวิว · เริ่มมีคำว่า "งานที่ไม่มีคนแตะเลย"
- **เงิน**: seat + usage · **บริการ deploy/integrate ขายได้แพงมาก** เพราะ demand > supply ของคนที่ทำเป็น
- **ตัวเร่ง**: tool-use แม่นขึ้น · **connector มาตรฐาน (MCP) โตระเบิด** — จาก ~100 servers (พ.ย. 2024) → registry ทางการนับ 9,652 server records (พ.ค. 2026), Glama index 19,831+ · company-operated servers 4,133 (+873% จากกลางปี 2025) · MCP ถูกโอนให้ Agentic AI Foundation ใต้ Linux Foundation (ธ.ค. 2025) = กลายเป็นมาตรฐานกลางจริง
- **ต้องมีก่อน**: ต่อระบบจริงได้ · มี audit log · มีคนที่ยอมรีวิว
- **สถานะ**: 🔵 **นี่คือที่ที่โลกส่วนใหญ่ยืนอยู่ตอนนี้** — Stacklok 2026 รายงาน 41% ขององค์กรซอฟต์แวร์ที่สำรวจอยู่ใน production แบบจำกัดหรือกว้างกับ MCP

### S2 — Agent as worker ⭐ **จุดเปลี่ยนที่สำคัญที่สุดสำหรับเรา**
- **โลก**: agent เป็นเจ้าของ workflow ทั้งเส้น มี SLA คนดูเฉพาะ exception · หัวหน้าเริ่มถามว่า "ทำไมต้องจ้างเพิ่ม"
- **เงิน**: **outcome pricing — จ่ายเมื่อได้ผลเท่านั้น** นี่คือครั้งแรกที่ลูกค้าจ่ายตาม *ผลลัพธ์* ไม่ใช่ *ที่นั่ง*
  - หลักฐานว่ามันเกิดแล้วจริง: **Zendesk $1.50/automated resolution** (committed) / $2.00 (PAYG) · **Intercom Fin $0.99/resolved conversation** · ช่วงตลาดทั่วไป ~$0.50–2.00/resolution
  - Zendesk คิดเงิน **เฉพาะเมื่อ AI ปิดเคสได้เองโดยไม่มีคนแตะ ล้มเหลว = ไม่คิดเงิน** → **ผู้ขายแบกความเสี่ยงทั้งหมด**
  - ขนาดที่แท้จริง (สำรวจเพิ่ม 2026-08-29): **~21.7% ของสัญญาซอฟต์แวร์องค์กรใน Q1 2026 เป็น outcome-based แล้ว และ 60% เป็น hybrid** ที่ผสม seat กับ outcome · Futurum 1H 2026: 27% ของผู้ซื้อชอบโครงสร้างแบบ outcome — **ใหญ่กว่าที่ประเมินไว้ตอนแรกมาก แต่ยังกระจุกใน customer support**
  - มีฝ่ายค้านชัดเจนแล้ว: Parloa เรียก outcome pricing ว่า *"กับดักที่สวยงาม"* ใน Forbes (ม.ค. 2026) → **ผู้ซื้อไม่ไว้ใจตัวเลขที่ vendor รายงานเอง ซึ่งคือเหตุผลที่คนกลางควรมีอยู่**
- **ตัวเร่ง**: eval ที่เชื่อถือได้ · observability · ประกัน/สัญญารับผิด · แรงกดดันจากคู่แข่งที่ประกาศตัวเลขประหยัด
- **ต้องมีก่อน** (โซ่ที่ยังขาดจริง ๆ วันนี้):
  1. **identity ของ agent** — ยังเป็นช่องโหว่เปิด แม้แต่ AP2 ก็ผูก mandate กับ key ของ *คน* ไม่ใช่ของ *agent*
  2. **spend control** ต่อ agent ต่อ task
  3. **eval ที่ทำหน้าที่เป็นสัญญา** — ทั้งสองฝ่ายต้องเห็นตรงกันว่า "สำเร็จ" แปลว่าอะไร
  4. **exception handling ที่มีคนจริงรออยู่**
- **สถานะ**: 🟡 **กำลังเปิด — customer support นำไปก่อน อุตสาหกรรมอื่นกำลังตาม นี่คือหน้าต่างของเรา**

> **ข้อสังเกตที่เปลี่ยนกลยุทธ์**: เมื่อคนขายแบกความเสี่ยง 100% เขาจะยอมจ่ายแพงมากเพื่อ (ก) รู้ว่าจะสำเร็จไหม *ก่อน* รับงาน และ (ข) พิสูจน์ต่อลูกค้าว่ามันสำเร็จจริง
> → **outcome pricing ไม่ได้แค่เปลี่ยนวิธีคิดเงิน มันสร้างตลาดใหม่ให้กับ "คนตรวจ"**

### S3 — Agent-to-agent economy
- **โลก**: agent ซื้อขาย/จ้างกันเอง คนไม่อยู่ใน loop รายธุรกรรม · การตลาดเปลี่ยนจาก "ทำให้คนคลิก" เป็น "ทำให้ agent เลือก"
- **เงิน**: ค่าธรรมเนียมต่อธุรกรรม · ค่า discovery · ค่า settlement · ค่าตัดสินข้อพิพาท
- **ตัวเร่ง**: มาตรฐานเริ่มลงตัวแล้วจริง — **AP2** (Google, v0.2.0 เม.ย. 2026, cryptographic mandate พิสูจน์ว่าคนอนุมัติ) · **ACP/UCP** ที่ชั้น checkout · **x402** สำหรับ machine-to-machine stablecoin
- **ต้องมีก่อน**: ระบบชื่อเสียง/attestation · การระงับข้อพิพาท · machine-readable offer · **และ agent identity ที่ยังไม่มีใครแก้ได้**
- **ความเสี่ยงที่ต้องจำ**: มีงานวิจัยความปลอดภัยชี้ช่องโหว่ free-riding ของ x402 แล้ว — โครงสร้างยังไม่นิ่ง
- **สถานะ**: 🟠 **ยังเช้าเกินไปสำหรับคนทุนน้อย** — protocol war ยังไม่จบ ลงตอนนี้เสี่ยงเลือกม้าผิด (แต่ **ต้องเฝ้า** เพราะถ้าลงตัวคือคลื่นลูกใหญ่)

### S4 — Full adoption
- **โลก**: บริษัท 3 คน output เท่าบริษัท 300 คน · org chart = กราฟของ agent · คนเหลืองาน 4 อย่าง: **ทิศทาง · รสนิยม · ความรับผิด · ความสัมพันธ์**
- **เงิน**: มูลค่าไหลไป compute/พลังงาน · ข้อมูลเฉพาะ · สินทรัพย์จริง · แบรนด์/ความไว้ใจ · บทบาทที่กฎหมายคุ้มครอง
- **ตัวเร่ง**: ต้นทุนต่อ task ต่ำกว่าค่าแรงชัดเจนในงานส่วนใหญ่
- **ตัวถ่วงที่แท้จริง**: **ไม่ใช่เทคโนโลยี แต่คือกฎหมาย ความรับผิด และความไว้ใจ** — สามอย่างนี้เดินช้ากว่าโมเดล 5-10 เท่าเสมอ
- **สถานะ**: ⚫ ไกล — ใช้เป็นเข็มทิศ ไม่ใช่แผน

## 4. ตอบคำถามตรง ๆ: เงินเริ่มแลกเปลี่ยนจริงตรงไหน

| คำถาม | คำตอบ |
|---|---|
| เงินจริงเริ่มเมื่อไร | **มีแล้วตั้งแต่ S0** แต่บางและ churn สูง |
| margin แข็งจริงเริ่มเมื่อไร | **S1→S2** — จุดที่ลูกค้ายอมจ่ายตามผลลัพธ์ |
| **แล้ว picks & shovels ล่ะ** | **เร็วกว่านั้น** — เราขายให้คนที่กำลังพยายามไปถึง S2 **เขาจ่ายก่อนที่ของเขาจะ work** |

**นี่คือเหตุผลเชิงโครงสร้างว่าทำไมบทบาท picks & shovels เหมาะกับสถานะเรา**: เราไม่ต้องรอให้ตลาด agent สำเร็จ เราได้เงินจากคนที่กำลังพยายาม ไม่ว่าเขาจะสำเร็จหรือไม่ — และตอนนี้มีคนพยายามเยอะมาก (funding เดือน ก.ค. 2026 อย่างเดียว ~$1.8B ใน 12+ ดีล)

**แต่มีอีกด้าน ที่ต้องเขียนไว้ให้เจ็บ**: ถ้าคลื่นนี้เป็นฟองสบู่ ลูกค้าเราคือคนกลุ่มแรกที่ตาย
→ เกณฑ์คัดกรอง: **เลือกสนามที่ลูกค้าเป็นคนที่มี P&L จริง ไม่ใช่คนที่มีแต่เงิน VC**

## 5. สิ่งที่โมเดลนี้อาจผิด (เขียนไว้เพื่อให้จับผิดตัวเองได้)

| สมมติฐาน | ถ้าผิดจะเป็นยังไง | ดูที่ signpost |
|---|---|---|
| Verification จะยังแพง | โมเดลตรวจงานตัวเองได้เชื่อถือได้ → ธุรกิจ eval หายไปเกือบหมด | SP-2, SP-3 |
| คอขวดคือ trust ไม่ใช่ capability | ถ้าองค์กรยอมรับความเสี่ยงเร็วกว่าที่คิด → S2 มาไวและ tooling รอบ ๆ ไม่ทัน | SP-4 |
| Vendor จะไม่ดูดชั้น infra | Anthropic/OpenAI/Google ship eval+identity+billing ครบในตัว → ทุกสนามกลุ่ม B/C ตาย | SP-5 |
| ตลาดโตต่อ | ฟองสบู่แตก งบ AI ถูกตัด ลูกค้า builder หายไป 60% | SP-6, SP-7 |
| S3 ยังไม่มา | ถ้า protocol ลงตัวเร็วกว่าคาด เราจะเข้าช้า | SP-8 |

**Tripwire**: ถ้ามี 2 ข้อขึ้นไปพลิกในไตรมาสเดียว → **หยุด กลับมาเขียนไฟล์นี้ใหม่** ไม่ใช่ปรับหน้างานไปเรื่อย ๆ
